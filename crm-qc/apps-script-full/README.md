# سامانه QC مستقل روی Google Sheets (Apps Script)

این پوشه نسخه‌ی **کاملاً مستقل** سامانه است: یک Web App در Google Apps Script که لینک اختصاصی دارد،
رابط کامل CRM را سرو می‌کند و همه‌ی داده‌ها را مستقیماً در **تب‌های جداگانه‌ی همان Google Sheet**
نگه می‌دارد. در این حالت هیچ سرور Node، هیچ میزبان و هیچ پوشه‌ی محلی لازم نیست.

> تفاوت با `crm-qc/apps-script/Code.gs`: آن نسخه فقط یک API/گزارش سبک برای اتصالِ نسخه‌ی Node به شیت بود.
> این نسخه (`apps-script-full`) خودِ سامانه است.

---

## فایل‌های این پوشه

| فایل | نقش | اندازه |
|---|---|---|
| `Code.gs` | بک‌اند Apps Script: خواندن/نوشتن تب‌ها، کش snapshot، ورود با رمز و نشست‌ها، محدودسازی داده، روتر API، منوی شیت، `doGet` | ~245 KB |
| `Index.html` | رابط کامل سامانه (همه‌ی صفحه‌ها، نمودارها، استایل و فونت) | ~864 KB |
| `CallReport.html` | ابزار مستقل «گزارش تماس روزانه»؛ در تب جدید باز می‌شود و دکمه‌ی «بازگشت به سامانه» دارد | ~394 KB |
| `appsscript.json` | مانیفست پروژه (منطقه زمانی، دامنه دسترسی، تنظیمات Web App) — برای استقرار با `clasp` | — |
| `Server.gs` | **فایل منبع** بک‌اند (مستقیم در Apps Script کپی نشود؛ build از آن `Code.gs` را می‌سازد) | — |

این فایل‌ها خروجی build هستند. دو طعم وجود دارد:

| build | دستور | کتابخانه‌ها | کاربرد |
|---|---|---|---|
| پیش‌فرض (CDN) | `npm --prefix crm-qc run build:apps-script` | Chart.js/SheetJS/ExcelJS/html2canvas/jsPDF/JSZip/Font Awesome/وزیرمتن از jsDelivr | فایل‌ها سبک‌اند و **راحت در ویرایشگر Apps Script paste می‌شوند**؛ برای باز شدن به اینترنت نیاز دارند |
| آفلاین | `npm --prefix crm-qc run build:apps-script:offline` → `apps-script-full/offline/` | همه‌چیز داخل فایل جاسازی می‌شود | بدون هیچ درخواست خارجی؛ فایل‌ها چند مگابایت‌اند و عملاً فقط با `clasp push` قابل استقرارند |

برای ساخت دوباره پس از هر تغییر در `crm-qc/public` یا `crm-qc/shared`:

```bash
npm --prefix crm-qc ci          # فقط بار اول (نسخه‌ی کتابخانه‌ها از node_modules خوانده می‌شود)
npm --prefix crm-qc run build:apps-script
```

## فعال‌سازی، گام به گام

### ۱) شیت و پروژه‌ی اسکریپت

1. یک Google Sheet تازه بسازید (یا شیت موجود را باز کنید). این شیت **دیتابیس** سامانه می‌شود.
2. از منوی شیت: `Extensions → Apps Script`.
3. در ویرایشگر، سه فایل بسازید با **دقیقاً همین نام‌ها**:
   - `Code.gs` → محتوای `apps-script-full/Code.gs` (کد پیش‌فرض `Code.gs` را کامل جایگزین کنید)
   - `Index.html` → از `+ → HTML` با نام `Index` و محتوای `apps-script-full/Index.html`
   - `CallReport.html` → از `+ → HTML` با نام `CallReport` و محتوای `apps-script-full/CallReport.html`
4. هر سه را `Save` کنید (Ctrl+S).

> **نکته‌ی اندازه‌ی فایل:** فایل‌های همین پوشه (build پیش‌فرض) سبک‌اند و معمولاً بدون مشکل در ویرایشگر paste
> می‌شوند. اگر از build آفلاین (`apps-script-full/offline/`) استفاده می‌کنید یا ویرایشگر هنگ کرد، روش `clasp`
> در انتهای همین صفحه فایل‌ها را بدون paste مستقیم منتقل می‌کند.

### ۲) راه‌اندازی تب‌های دیتابیس

1. در نوار بالای ویرایشگر، تابع `setupStandaloneApp` را انتخاب و `Run` بزنید.
2. اولین بار، گوگل درخواست اجازه می‌کند: `Review permissions` → حساب خودتان → `Advanced` →
   `Go to <project name> (unsafe)` → `Allow`. (پیام «unsafe» فقط چون برنامه توسط خودتان نوشته شده است.)
3. شیت را refresh کنید. ۲۳ تب زیر ساخته می‌شود و منوی **سامانه QC مستقل** به شیت اضافه می‌شود:

| تب | محتوا |
|---|---|
| `Agents` | کارشناسان: شناسه، داخلی، نام، تیم، فعال، زیرگروه، aliasها |
| `Tickets` | ارزیابی تیکت: ریز المان‌ها، ردلاین، نمره، تاریخ بررسی/تیکت، کارشناس QC |
| `Socials` | ارزیابی سوشال: تاریخ/ساعت دریافت و پاسخ، SLA، مدت کاری، المان‌ها، نمره |
| `Calls` | ریت تماس: نمره، ردلاین، المان‌ها، فرم/تیم، فایل و ردیف منبع |
| `QC_Agents` | فهرست کارشناسان کنترل کیفیت |
| `Actions` | اقدامات اصلاحی (با ستون `agent`) |
| `Reminders` | یادآورهای کارشناس |
| `Action_Types` | نوع اقدام‌ها |
| `Settings` | وزن‌ها، آستانه SLA، ساعت کاری، روزهای تعطیل، نام سازمان، `authMode` و `defaultPreset` (کلید/مقدار) |
| `Lists` | فهرست‌های کشویی (پیام‌رسان، وضعیت پاسخ، دلیل تأخیر) |
| `Criteria` | تعریف المان‌های ریت تماس هر تیم/فرم (JSON) |
| `Meta` | `datasetId`، `createdAt`، `revision` و شمارنده‌های `seq` |
| `Call_Metadata` | متادیتای ایمپورت تماس‌ها (`callImport`, `callSync`, `callRaw`) |
| `Call_Report_Experts` / `Call_Report_Access` | تنظیمات ابزار گزارش تماس روزانه |
| **`Fiscal_Months`** | بازه‌های آماده‌ی ماه مالی: `id, name, from, to, note` |
| **`QC_Users`** | کاربران ورود و دسترسی‌ها: `id, name, password, role, active, exts, agents, teams, note` |
| **`Elements`** | المان‌ها به‌صورت تخت: `scope, team, form, key, label, excelKey, active, aliases, order` |
| **`Monthly_Summary`** | خلاصه‌ی ماهانه‌ی آماده (به‌ازای هر کارشناس و هر ماه) برای بررسی و خروجی سریع |

اگر شیت از قبل داده داشته باشد، `setupStandaloneApp` آن را **پاک نمی‌کند**؛ فقط ساختار را کامل می‌کند و
داده‌ی موجود را می‌خواند. دیتای نمونه (`data/seed.json`: ۶۵ کارشناس و تنظیمات پیش‌فرض) فقط وقتی شیت
کاملاً خالی است نوشته می‌شود.

> **ویرایش مستقیم روی شیت:** چهار تب آخر طوری طراحی شده‌اند که بتوانید بدون باز کردن سامانه، مستقیم روی
> شیت (یا با کپی/پیست از اکسل) بنویسید: بازه‌های ماه مالی، کاربران و دسترسی‌ها، و نام/ستون المان‌ها.
> سامانه در خواندن بعدی همان ردیف‌ها را برمی‌دارد. فقط ستون‌های JSON را دستی نشکنید.

### ۳) ساخت لینک اختصاصی (Deploy)

1. در ویرایشگر: `Deploy → New deployment`.
2. کنار چرخ‌دنده نوع استقرار را `Web app` انتخاب کنید.
3. `Description`: مثلاً «سامانه QC — نسخه ۱».
4. `Execute as`: **Me** (حساب خودتان؛ دسترسی شیت از اعتبار شما می‌آید).
5. `Who has access`: بر اساس سیاست سازمان —
   - `Only myself` = فقط شما (امن‌ترین حالت برای تست)،
   - `Anyone within <domain>` = همکاران دامنه‌ی سازمانی (پیشنهادی)،
   - `Anyone` = هر کسی با لینک؛ در این حالت حتماً ورود با رمز را فعال کنید (بخش بعد).
6. `Deploy` → `Authorize access` (اگر خواست) → **Web app URL** را کپی کنید.

همان URL، لینک مستقل سامانه است؛ مثل یک سایت باز می‌شود و می‌توانید آن را بوک‌مارک یا در موبایل
«Add to Home Screen» کنید.

### ۴) اولین ورود و ساخت حساب مدیر

1. لینک را باز کنید. تا وقتی **هیچ کاربر فعالی با رمز** در تب `QC_Users` نباشد، سامانه مثل قبل بدون ورود
   باز می‌شود (حالت `auto`) و بالای صفحه کارت «راه‌اندازی دسترسی مدیر» می‌آید.
2. یک نام و رمز برای خودتان بسازید (حداقل ۴ نویسه). از همان لحظه ورود با رمز **اجباری** می‌شود.
3. رمز به‌صورت اثر انگشت SHA-256 با نمک ذخیره می‌شود (`sha256$<salt>$<hash>`)؛ اگر رمزی را مستقیم روی
   تب `QC_Users` به‌صورت متن ساده بنویسید هم پذیرفته می‌شود تا مدیریت از داخل شیت ممکن بماند.
4. از صفحه‌ی **مدیریت QC** (فقط مدیر) برای بقیه کاربر و رمز بسازید و مشخص کنید هر کارشناس QC کدام
   کارشناسان/داخلی‌ها/تیم‌ها را ببیند.

### ۵) تست سریع

- لینک را باز کنید: باید داشبورد با داده‌ی شیت بالا بیاید و نشانگر بالای صفحه **Google Sheets** باشد.
- یک ارزیابی تیکت یا سوشال ثبت کنید → بلافاصله ردیف جدید در تب `Tickets` / `Socials` ظاهر می‌شود.
- مستقیم در شیت یک ردیف اضافه/ویرایش کنید → در سامانه `Refresh` بزنید؛ تغییر خوانده می‌شود
  (تریگر `onChange` کش را باطل می‌کند). اگر تغییری دیده نشد، منوی شیت →
  `سامانه QC مستقل → خواندن تازه از شیت (پاک‌کردن کش)`.
- برگه‌ی **گزارش تماس** در این نسخه یک «لانچر» است: ابزار گزارش تماس در تب جدید (یا همین صفحه) باز می‌شود
  و داخل خودش دکمه‌ی بازگشت به سامانه دارد (دلیلش در بخش «گزارش تماس» پایین توضیح داده شده).
- منوی شیت: `سامانه QC مستقل` شامل چهار فرمان است —
  `راه‌اندازی / بررسی تب‌های سامانه` (همان `setupStandaloneApp`)،
  `خواندن تازه از شیت (پاک‌کردن کش)`، `بازسازی تب خلاصه ماهانه` و
  `بستن همه نشست‌های فعال (خروج اجباری)`.

## ورود با رمز، نقش‌ها و دسترسی داده (تب `QC_Users`)

| نقش | صفحه‌ها | داده |
|---|---|---|
| `admin` (مدیر سیستم) | همه‌ی صفحه‌ها، شامل چهار صفحه‌ی مدیریتی «تغییر المان‌ها»، «مدیریت پایه»، «مدیریت کارشناسان»، «مرکز داده» + «مدیریت QC» | همه‌ی کارشناسان و همه‌ی رکوردها، داشبورد و گزارش‌ها بدون محدودیت |
| `qc` (کارشناس QC) | فقط صفحه‌های عملیاتی: داشبورد، ثبت/سوابق تیکت و سوشال، گزارش‌ها، پرونده کارشناس، مرجع کارشناسان، تحلیل ریت تماس، گزارش تماس | فقط کارشناسانی که مدیر اجازه داده (و رکوردهای همان کارشناسان) |

ستون‌های تب `QC_Users`:

| ستون | مقدار |
|---|---|
| `name` | نام کارشناس QC — همان نامی که در فرم‌ها به‌عنوان «کارشناس کنترل کیفیت» ثبت می‌شود |
| `password` | اثر انگشت hash یا متن ساده (دست‌کم ۴ نویسه) |
| `role` | `admin` یا `qc` |
| `active` | `1`/`0` (خالی یعنی فعال) — کاربر غیرفعال نمی‌تواند وارد شود |
| `exts` | داخلی‌های مجاز، جداشده با ویرگول (مثلاً `3073,3082`)؛ اعداد فارسی هم پذیرفته می‌شود |
| `agents` | نام کارشناسان مجاز (جداشده با ویرگول) |
| `teams` | تیم‌های مجاز (جداشده با ویرگول) — همه‌ی کارشناسان آن تیم |
| `note` | یادداشت دلخواه |

قواعد دسترسی:

- اتحاد سه ستون `exts` + `agents` + `teams` دسترسی کاربر را می‌سازد.
- `*` یا `all` یا `همه` در هر ستون = بدون محدودیت.
- **دسترسی خالی یعنی هیچ داده‌ای** (کاربر فقط پوسته‌ی خالی می‌بیند) — پس حتماً یکی از سه ستون را پر کنید.
- هر کارشناس QC می‌تواند ارزیابی ثبت/ویرایش کند، اما فقط برای کارشناسان مجاز خودش؛ نوشتن روی رکورد
  کارشناسِ دیگر با خطای «به داده‌ی کارشناس «…» دسترسی ندارید» رد می‌شود.
- APIهای مدیریتی (`Criteria`، `Settings`، `QC_Users`، `Fiscal_Months`، `Elements`، بک‌اپ، مرکز داده،
  مدیریت کارشناسان، اتصال به شیت) برای نقش `qc` بسته‌اند.
- حالت ورود در تب `Settings` کلید `authMode` ذخیره می‌شود و از صفحه‌ی «مدیریت QC» هم قابل تغییر است:
  `auto` (پیش‌فرض: با اولین کاربر فعال، ورود اجباری می‌شود)، `on` (همیشه روشن)، `off` (بدون رمز و بدون
  محدودیت داده — فقط برای محیط آزمایشی).
- نشست‌ها در `PropertiesService` با کلید `qctok@<epoch>@<token>` نگه داشته می‌شوند و ۶ ساعت بی‌فعالیتی
  دارند. `بستن همه نشست‌های فعال (خروج اجباری)` از منوی شیت، همه را یک‌جا باطل می‌کند (مثلاً وقتی رمزی لو رفته).

## بازه‌ی آماده‌ی ماه مالی (تب `Fiscal_Months`)

فیلتر تاریخ بالای سامانه یک dropdown «بازه آماده» دارد که گزینه‌هایش **از همین تب خوانده می‌شود**:

| ستون | نمونه |
|---|---|
| `name` | `مهر ۱۴۰۵` |
| `from` | `1405/07/01` |
| `to` | `1405/07/30` |
| `note` | اختیاری |
| `id` | اختیاری — اگر خالی باشد سامانه خودش می‌سازد |

- گزینه‌ها: `ماه مالی جاری`، `ماه مالی قبل` و بعد همه‌ی ماه‌ها به‌تفکیک نام.
- «جاری» یعنی ماهی که امروز داخل بازه‌اش است؛ اگر امروز در هیچ بازه‌ای نباشد، آخرین ماهی که شروع شده
  انتخاب می‌شود.
- ردیف با تاریخ نامعتبر یا بازه‌ی وارونه (`from` بعد از `to`) نادیده گرفته می‌شود تا کل فیلتر نشکند.
- می‌توانید ۱۲ ماه را از صفحه‌ی «مدیریت پایه» با یک دکمه بسازید، یا ردیف‌ها را از اکسل کپی و در تب پیست کنید.
- کلید `defaultPreset` در تب `Settings` مشخص می‌کند سامانه با کدام بازه بالا بیاید (`all`، `cur`، `prev`
  یا `fm:<id>` / `fm:cur` / `fm:prev`).

## تغییر المان‌ها از روی شیت (تب `Elements`)

برگه‌ی «تغییر المان‌ها» در سامانه همان چیزی را ویرایش می‌کند که در تب `Elements` به‌صورت **تخت و خوانا**
نوشته شده است؛ پس می‌توانید مستقیم روی شیت هم تغییرشان بدهید:

| ستون | معنا |
|---|---|
| `scope` | `form` (فرم عمومی) یا `team` (اختصاصی یک تیم) |
| `team` | نام تیم وقتی `scope=team` است |
| `form` | نوع فرم: `tele`، `account`، `mlm` (یا `ticket`/`social` در پیکربندی فرم‌ها) |
| `key` | شناسه‌ی داخلی المان (تغییر ندهید) |
| `label` | **نام فارسی المان** که در سامانه و خروجی‌ها دیده می‌شود |
| `excelKey` | **نام ستون در فایل اکسل دریافتی** که مقدار المان از آن خوانده می‌شود |
| `active` | `1`/`0` |
| `aliases` | نام‌های قبلی ستون اکسل، جداشده با `|` |
| `order` | ترتیب نمایش |

- اگر `excelKey` را عوض کنید، سامانه **خودکار نام قبلی را به `aliases` منتقل می‌کند** تا سوابق قدیمی که با
  ستون قبلی وارد شده‌اند همچنان درست خوانده شوند.
- هر ردیف با `key` خالی نادیده گرفته می‌شود؛ اگر `label` را خالی بگذارید، برچسب قبلی حفظ می‌شود.
- تغییر المان‌ها نسخه‌ی پیکربندی را بالا می‌برد؛ اگر دو نفر هم‌زمان ویرایش کنند، ویرایش دوم با خطای
  «تنظیمات هم‌زمان تغییر کرده است» رد می‌شود تا کار کسی پاک نشود.

## خلاصه‌ی ماهانه و سرعت محاسبات (تب `Monthly_Summary`)

برای اینکه گزارش‌ها هر بار از صفر محاسبه نشوند، دو لایه اضافه شده است:

1. **کش تحلیل (`CacheService`)** — پاسخ تحلیل‌های سنگین با کلید
   `qcan@<revision>#<hash(user+url)>` کش می‌شوند (TTL شش ساعت، تکه‌تکه برای پاسخ‌های بزرگ). با هر
   نوشتن، `revision` بالا می‌رود و کش‌های قدیمی خودبه‌خود بی‌اثر می‌شوند. این کش **روی شیت نمی‌نویسد**،
   پس تریگر `onChange` را تحریک نمی‌کند.
2. **تب `Monthly_Summary`** — همان اعداد گزارش ترکیبی، اما به‌ازای هر «کارشناس × ماه» از پیش محاسبه و
   روی شیت نوشته شده: تعداد و میانگین تیکت/سوشال/تماس، ردلاین‌ها، کارشناسان QC، تعداد کل و میانگین
   ترکیبی. برای راستی‌آزمایی، فیلترکردن در اکسل و خروجی گرفتن مستقیم.
   - بازسازی: منوی شیت → `بازسازی تب خلاصه ماهانه` (تابع `rebuildMonthlySummary`).
   - داخل سامانه هم مسیر `/api/monthly-summary` همان داده را می‌دهد (برای کارشناس QC محدودشده).

## گزارش تماس در این نسخه (بدون `refused to connect`)

گوگل صفحه‌ی وب‌اپ را داخل یک فریم شنی (sandbox) سرو می‌کند و اجازه نمی‌دهد همان وب‌اپ داخل فریمِ خودش
باز شود؛ نتیجه خطای **`refused to connect`** است. به همین دلیل در نسخه‌ی Apps Script:

- برگه‌ی «گزارش تماس» دیگر iframe نمی‌سازد؛ دو دکمه دارد: **باز کردن در تب جدید** و **باز کردن در همین صفحه**.
- نشانی همان `Web app URL` شما با `?page=call-report` است و بازه‌ی تاریخ فعال و حالت رنگ (تاریک/روشن)
  به‌صورت پارامتر همراهش منتقل می‌شود.
- خودِ `CallReport.html` یک نوار «بازگشت به سامانه» دارد (پایین-چپ، در چاپ دیده نمی‌شود) و داده‌اش را در
  تب‌های `Call_Report_Experts` و `Call_Report_Access` نگه می‌دارد.
- در نسخه‌ی Node (سرور محلی) همان برگه همچنان گزارش را **داخل یک فریم هم‌ریشه** نشان می‌دهد، چون آنجا
  مشکل فریم تودرتو وجود ندارد.

## کار هم‌زمان چند کارشناس QC

- **نوشتن‌ها زیر قفل:** هر درخواست غیر GET با `LockService` اجرا می‌شود و داده را **تازه از شیت** می‌خواند
  (نه از کش) تا نوشتن دیگران پاک نشود؛ درخواست دوم تا ۳۰ ثانیه منتظر می‌ماند.
- **تشخیص ویرایش همزمان (۴۰۹):** هر فرم، زمان آخرین ویرایش رکورد (`baseUpdatedAt`) را همراه ذخیره
  می‌فرستد. اگر در فاصله‌ی باز بودن فرم، کس دیگری همان رکورد را ویرایش کرده باشد، سامانه به‌جای بازنویسی
  کورکورانه یک گفت‌وگو نشان می‌دهد: «بارگذاری نسخه‌ی تازه» یا «تغییرات من جایگزین شود».
- **همگام‌سازی خودکار:** هر مرورگر هر ~۴۵ ثانیه `/api/revision` را می‌پرسد (فقط وقتی تب فعال است). اگر
  شماره‌ی بازنگری عوض شده باشد، نشانگر بالای صفحه («همگام‌سازی») روشن می‌شود و با یک کلیک داده‌ی تازه
  بارگذاری می‌شود؛ بعد از هر ثبت هم خودش تازه می‌شود.
- **محیط کاری جدا برای هر کاربر:** تنظیمات محلی مرورگر (بازه‌ی تاریخ انتخابی، فیلترها، ستون‌های جدول)
  با کلید اختصاصی همان کاربر ذخیره می‌شود، پس سلیقه‌ی یک کارشناس روی کار دیگری اثر نمی‌گذارد.
- **خواندن‌ها بدون قفل:** GETها از کش snapshot سرو می‌شوند و موازی اجرا می‌شوند؛ برای کارشناس QC هم
  همان کش با کلید مخصوص خودش (شامل محدوده‌ی دسترسی) استفاده می‌شود تا داده‌ی محدودشده با داده‌ی مدیر
  قاطی نشود.

## رفتار داده و سرعت در این نسخه

- **شیت تنها منبع داده است.** همه‌ی رکوردها در تب‌های همان شیت نگه داشته می‌شوند و منطق ثبت/نمره‌دهی
  سمت Apps Script اجرا می‌شود.
- **کش snapshot (دلیل سرعت):** کل دیتابیس یک‌بار از تب‌ها خوانده و به‌شکل یک snapshot در `CacheService`
  نگه داشته می‌شود. هر snapshot یک **revision** دارد. خواندن‌ها (GET) به‌جای ده‌ها فراخوانی `SpreadsheetApp`
  تنها ~۲ فراخوانی (خواندن revision + کش) دارند و **بدون قفل** و به‌صورت موازی سرو می‌شوند.
- **باطل‌سازی کش:** هر نوشتنِ خودِ سامانه، revision تازه را همراه snapshot جدید منتشر می‌کند
  (write-through). ویرایش مستقیم شیت را تریگر `onChange` (تابع `crmqcOnSheetChange` که `setupStandaloneApp`
  نصب می‌کند) باطل می‌کند؛ اگر تریگر نصب نباشد هم کش حداکثر پس از ۱۰ دقیقه منقضی می‌شود.
- **عبور دستی از کش:** منوی شیت → `سامانه QC مستقل → خواندن تازه از شیت (پاک‌کردن کش)`
  (تابع `refreshFromSheet`) فوراً داده‌ی فعلی شیت را می‌خواند و کش را تازه می‌کند.
- **نوشتن حداقلی:** فقط سطرهای واقعاً تغییریافته نوشته می‌شوند — ثبت رکورد جدید = یک `setValues` روی
  دُمِ تب، حذف = `deleteRows`، ویرایش چند سطر = پچ همان rangeها؛ بدون `clearContents` و بدون استایل‌دادن
  دوباره‌ی هدر در هر نوشتن.
- **کش سمت مرورگر:** پاسخ GETهای یکسان در رابط تا ۴ ثانیه نگه داشته و درخواست‌های تکراریِ هم‌زمان ادغام
  می‌شوند؛ هر ثبت/ویرایش این کش را بلافاصله خالی می‌کند.
- **ورود اکسل ریت تماس:** پوشه‌ی محلی `data/calls` در این نسخه وجود ندارد. از برگه‌ی **مرکز داده**
  فایل‌های `.xlsx` را آپلود کنید؛ همان منطق تشخیص فرم/تیم و ادغام امن اجرا و نتیجه در تب `Calls` نوشته می‌شود.
- **بک‌اپ:** از برگه‌ی مرکز داده خروجی JSON بگیرید، یا یک کپی از خود شیت (`File → Make a copy`) نگه دارید.
- **تاریخ‌ها** به همان شکل جلالی `1405/07/22` در تب‌ها ذخیره می‌شوند. ستون‌های JSON (مثل `elements`) را
  دستی نشکنید.

## محدودیت‌هایی که باید بدانید

- Google Sheets برای حجم کم تا متوسط مناسب است؛ سهمیه‌ی اجرای Apps Script و محدودیت نرخ API دارد.
  با چند هزار ردیف مشکلی نیست، اما برای بار سنگین/چند کاربر هم‌زمان دیتابیس واقعی بهتر است.
- ورود با رمز، **لایه‌ی سامانه** است (رمزها hash‌شده در تب `QC_Users`). این جایگزین کنترل دسترسی خودِ
  گوگل نیست: اگر لینک را `Anyone` گذاشته‌اید، هر کسی می‌تواند صفحه‌ی ورود را ببیند و به شیتِ پشتِ برنامه
  دسترسیِ مستقیم ندارد، ولی بهتر است سطح Deploy را هم محدود نگه دارید.
- `CacheService` و `PropertiesService` محدودیت حجم دارند؛ snapshotهای خیلی بزرگ تکه‌تکه ذخیره می‌شوند و
  اگر از سقف بگذرند سامانه به خواندن مستقیم از شیت برمی‌گردد (کندتر، اما درست).
- هر تغییر در کد، نیاز به `Deploy → Manage deployments → Edit → New version` دارد تا روی لینک اعمال شود.
  پس از به‌روزرسانی `Code.gs` یک بار هم `setupStandaloneApp` را دوباره اجرا کنید تا تریگر `onChange` نصب بماند.
- ابزار «گزارش تماس روزانه» تنظیمات خودش (کارشناسان/پروفایل دسترسی) را در دو تب اختصاصی نگه می‌دارد.

## استقرار با `clasp` (وقتی فایل‌ها برای paste بزرگ‌اند)

```bash
npm install -g @google/clasp
clasp login
cd crm-qc/apps-script-full
clasp create --type sheets --title "سامانه QC" --rootDir .   # یا clasp clone <scriptId>
clasp push                                                   # هر سه فایل + appsscript.json
clasp open
```

سپس در ویرایشگر `setupStandaloneApp` را اجرا و طبق بخش ۳ استقرار Web App را بسازید.

## اگر خواستید هر دو نسخه را داشته باشید

نسخه‌ی Node (با پوشه‌ی `data/calls` و واچر خودکار) همچنان کار می‌کند و از تب **اتصال به گوگل شیت**
(`#/sheets`) به یک شیت وصل می‌شود؛ آن مسیر از `crm-qc/apps-script/Code.gs` استفاده می‌کند و به این
پوشه ربطی ندارد. برای جلوگیری از دو منبع داده، یکی از دو حالت را انتخاب کنید:

- فقط Apps Script مستقل (این پوشه) — بدون سرور،
- یا فقط Node + شیت به‌عنوان مخزن/گزارش.
