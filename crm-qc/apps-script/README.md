# اتصال Google Sheets به سامانه QC

## معماری در یک نگاه

برای استفاده از **رابط کامل فعلی**، Node همچنان روی یک میزبان اجرا می‌شود؛ Google Sheets نقش مخزن داده و محل گزارش را می‌گیرد. Apps Script داخل شیت یک API امن برای خواندن/نوشتن، منو و گزارش ساده‌ی داخلی می‌دهد، اما خود شیت میزبان Node یا رابط کامل فعلی CRM نیست.

سه روش اتصال:

1. **Apps Script Web App (پیشنهادی برای شروع):** خواندن و نوشتن دوسویه؛ با توکن API و بدون فایل Google Cloud.
2. **Service Account:** اتصال سازمانی مستقیم به Sheets API؛ مناسب سروری که کلید را به‌صورت امن نگه می‌دارد.
3. **API Key:** فقط خواندن شیت عمومی؛ بدون پوش به شیت و بدون ارسال گزارش.

فایل آماده‌ی اسکریپت اینجاست: `crm-qc/apps-script/Code.gs`.

---

## روش پیشنهادی: Apps Script Web App

### ۱. ساختار اولیه در شیت

1. یک Google Sheet بسازید.
2. از `Extensions → Apps Script` وارد ویرایشگر شوید.
3. کد `Code.gs` همین پوشه را جایگزین کد پیش‌فرض کنید و Save بزنید.
4. یک‌بار تابع `setupSheets` را در ویرایشگر اجرا کنید و اجازه‌های لازم را تأیید کنید.
5. شیت را دوباره باز/refresh کنید؛ منوی **سامانه QC** ظاهر می‌شود. تب‌های `Agents`, `Tickets`, `Socials`, `Calls`, `Actions`, `Settings` ایجاد می‌شوند.

### ۲. ساخت توکن و انتشار Web App

1. از منوی شیت: `سامانه QC → راه‌اندازی / چرخش توکن API` را بزنید؛ توکن بلند و تصادفی را کپی کنید. اگر گم شد، چرخش توکن، توکن قبلی را باطل می‌کند.
2. در Apps Script بروید به `Deploy → New deployment → Web app`.
3. اجرا به‌عنوان خودتان (`Execute as: Me`) را انتخاب کنید. سطح دسترسی را با سیاست سازمانتان هماهنگ کنید؛ فقط در صورتی دسترسی عمومی بدهید که مجاز است.
4. Deploy کنید و URL را بردارید. با هر تغییر نسخه‌ی Code.gs ممکن است لازم باشد deployment را ویرایش/به‌روزرسانی کنید.
5. در سامانه‌ی Node مسیر `#/sheets` را باز کنید؛ حالت Web App، URL و توکن را وارد و «فعال‌سازی» و سپس «ذخیره تنظیمات» را بزنید.

توکن در `crm-qc/data/sheets-config.json` روی سرور ذخیره می‌شود؛ این فایل و فایل JSON اکانت سرویس در `.gitignore` هستند. توکن یا کلید خصوصی را در چت، Git یا مرورگرهای عمومی قرار ندهید.

### ۳. انتخاب جهت اولین همگام‌سازی

همگام‌سازی خودکار تا وقتی اولین جهت را انتخاب نکرده‌اید شروع نمی‌شود:

- **اطلاعات فعلی سامانه → شیت:** در صفحه‌ی اتصال دکمه‌ی «ارسال اطلاعات سامانه به شیت» را بزنید. تب‌های داده‌ی مربوط با دیتای فعلی سامانه جایگزین می‌شوند؛ این کار را فقط بعد از بک‌اپ انجام دهید.
- **شیت → سامانه:** دکمه‌ی «خواندن / همگام‌سازی از شیت» را بزنید و در پنجره‌ی انتخاب، «ادغام» یا «جایگزینی» را انتخاب کنید. گزینه‌ی جایگزینی داده‌ی فعلی سامانه در تب‌های مدیریت‌شده را حذف می‌کند و تأیید جدا می‌خواهد.

پس از آن، تنظیم «فاصله خواندن از شیت» زمان بررسی تغییرهای شیت را تعیین می‌کند (پیش‌فرض ۶۰ ثانیه). ثبت در سامانه، اگر «ارسال خودکار» روشن باشد، پس از چند ثانیه به شیت می‌رود. اتصال، لحظه‌ای نیست.

## سیاست همگام‌سازی و حذف داده

- **ادغام امن** (پیش‌فرض): رکوردهای ورودی با شناسه به‌روزرسانی/اضافه می‌شوند؛ نبودن یک ردیف در شیت باعث حذف رکورد محلی نمی‌شود. این گزینه برای شروع امن‌تر است.
- **شیت مرجع اصلی:** تب‌ها مرجع داده هستند؛ ویرایش‌ها و حذف ردیف در شیت در Pull بعدی اعمال می‌شوند. قبل از انتخاب، یک‌بار دیتای سامانه را در شیت بنویسید و بک‌اپ بگیرید.
- **ارسال به شیت** تب‌های مدیریت‌شده را به‌طور کامل بازنویسی می‌کند، نه اینکه فقط انتهای جدول را اضافه کند. این کار از تکراری‌شدن داده جلوگیری می‌کند، اما ممکن است ویرایش مستقیمی که هنوز Pull نشده با ارسال بعدی جایگزین شود.
- اگر شیت و سامانه هم‌زمان یک رکورد را ویرایش کنند، آخرین همگام‌سازی برنده می‌شود. برای جلوگیری از تعارض، ویرایش گروهی را در یک طرف انجام دهید و بعد Pull/Push را صریح اجرا کنید.
- شناسه‌ی `id` در Tickets/Socials/Agents و `syncId` در Calls را دستی تغییر ندهید. ستون `extra` برای حفظ فیلدهای افزوده‌ی سامانه است؛ آن را حذف/ویرایش نکنید.

### تب‌ها و اطلاعات

| تب | محتوا |
|---|---|
| `Agents` | شناسه، نام، تیم، داخلی، فعال/بایگانی، aliasها |
| `Tickets` | ریز فیلدهای امتیازدهی، تاریخ بررسی/تیکت، کارشناس QC و توضیحات |
| `Socials` | تاریخ/ساعت پیام، SLA، معیارها، امتیاز و توضیحات |
| `Calls` | ریت تماس، تیم/فرم، ردلاین، المان‌ها، تاریخ‌ها، شناسه‌ی همگام‌سازی |
| `Actions` | اقدامات اصلاحی و نتیجه/وضعیت |
| `Settings` | تنظیمات و فهرست‌های لازم برای بازسازی وضعیت سامانه |
| `QC_Report_YYYY-MM-DD` | گزارش تجمیعی ارسالی از صفحه اتصال (تب گزارش جداگانه) |

ردیف اول هر تب Header است. تاریخ‌ها را به شکل جلالی `1405/07/22` نگه دارید. برای ورود دستی بهتر است ستون تاریخ در حالت Plain text باشد. ستون `extra` می‌تواند JSON داشته باشد؛ Google Sheets سلول‌های خیلی بزرگ (حدود ۵۰ هزار نویسه) را نمی‌پذیرد.

## گزارش

- از مسیر `#/sheets` دکمه‌ی **ارسال گزارش عملکرد به شیت** خلاصه‌ی عملکرد را برای بازه‌ی سراسری انتخاب‌شده در تب گزارش تازه می‌نویسد.
- داخل خود Sheet نیز `سامانه QC → نمایش داشبورد در سایدبار` و `تولید گزارش در شیت Reports` در دسترس‌اند.
- گزارش‌های تولیدشده در تب جدا قرار می‌گیرند و تب‌های داده را جایگزین نمی‌کنند.

## Service Account (اتصال مستقیم سازمانی)

1. در Google Cloud یک پروژه بسازید و Google Sheets API را فعال کنید.
2. یک Service Account بسازید و کلید JSON ایجاد کنید.
3. کلید را فقط روی میزبان Node در `crm-qc/data/sheets-credentials.json` بگذارید.
4. همان ایمیل Service Account را به Google Sheet با سطح Editor دعوت کنید.
5. در صفحه `#/sheets` حالت Service Account و Spreadsheet ID را وارد کنید.

نمونه‌ی تنظیمات روی سرور (روش Web App؛ **توکن واقعی را در فایل خصوصی `sheets-config.json` نگه دارید**):

```json
{
  "enabled": true,
  "initialized": false,
  "mode": "webapp",
  "syncPolicy": "merge",
  "spreadsheetId": "SPREADSHEET_ID",
  "webAppUrl": "https://script.google.com/macros/s/DEPLOYMENT_ID/exec",
  "webAppToken": "TOKEN_GENERATED_IN_THE_SHEET",
  "syncIntervalSec": 60,
  "pushOnWrite": true,
  "sheets": {
    "agents": "Agents", "tickets": "Tickets", "socials": "Socials",
    "calls": "Calls", "actions": "Actions", "settings": "Settings"
  }
}
```

نمونه‌ی Service Account:

```json
{
  "enabled": true,
  "initialized": false,
  "mode": "service_account",
  "syncPolicy": "merge",
  "spreadsheetId": "SPREADSHEET_ID",
  "credentialsFile": "data/sheets-credentials.json",
  "syncIntervalSec": 60,
  "pushOnWrite": true
}
```

`crm-qc/data/sheets-config.example.json` فایل نمونه‌ی بدون راز است؛ مستقیماً آن را به‌عنوان تنظیمات فعال کپی نکنید.

## APIهای سامانه

| متد | مسیر | کاربرد |
|---|---|---|
| `GET` | `/api/sheets/status` | وضعیت Poll/Push و آخرین خطا |
| `GET` | `/api/sheets/config` | تنظیمات بدون مقدار secret |
| `PUT` | `/api/sheets/config` | ذخیره تنظیمات اتصال |
| `POST` | `/api/sheets/pull` | خواندن/ادغام فوری؛ `{initialize:true, initialPolicy:"merge"|"sheet"}` برای شروع |
| `POST` | `/api/sheets/push` | نوشتن کامل تب‌های تحت مدیریت |
| `GET` | `/api/sheets/preview` | پیش‌نمایش پنج ردیف اول |
| `POST` | `/api/sheets/report` | گزارش عملکرد به شیت |

## نکته‌های استقرار

- برای نصب وابستگی‌ها و اجرای برنامه: `npm --prefix crm-qc ci` سپس `npm --prefix crm-qc start`.
- گوگل‌شیت برای حجم کم تا متوسط مناسب است؛ محدودیت نرخ API، اندازه‌ی سلول و سهمیه‌ی اجرای Apps Script وجود دارد. برای بار بالا یا چندین ویرایش هم‌زمان، PostgreSQL/MySQL مناسب‌تر است.
- API فعلی سامانه احراز هویت کاربری ندارد. قبل از انتشار در اینترنت عمومی، برای تمام برنامه Reverse Proxy/SSO یا احراز هویت سازمانی بگذارید؛ مخفی‌ماندن URL یا توکن Apps Script جایگزین ورود کاربران سامانه نیست.
- هیچ‌کدام از اطلاعات ورود گوگل از کاربر گرفته یا داخل Git ذخیره نمی‌شود؛ مالک شیت باید اتصال را در محیط خودش فعال کند.
