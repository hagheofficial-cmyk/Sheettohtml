# Sheettohtml

سامانه‌ی کنترل کیفیت (QC) با پنل ریت تماس، گزارش‌گیری کارشناسی و داشبورد مدیریتی — پشتیبان قدم‌به‌قدم سامانه تیکت و سوشال.

## ساختار

| پوشه | توضیح |
|------|-------|
| `crm-qc/` | نسخه‌ی سروروار (Node) — API + واچر پوشه‌ی `data/calls/` — توصیه‌شده |
| `HTML اصلی/` | نسخه‌ی تک‌فایل-مرورگری (localStorage) — بدون سرور |
| `data/calls/` | پوشه‌ی اکسل‌های ریت QC تیم‌ها (تلفنی / اکانت / MLM) — هر ۱۵ ثانیه خوانده می‌شود |

## راه‌اندازی سریع

```bash
cd crm-qc
npm install
node server.js          # → http://localhost:8000
```

سپس:
1. فایل اکسیل فرمیگان QC تیم‌ها (telfany.xlsx / acc.xlsx / mlm.xlsx) را داخل `crm-qc/data/calls/` بگذار. سامانه خودکار تشخیص و این‌جست می‌کند.
2. مرورگر → `http://localhost:8000` → از منو «تحلیل ریت تماس» — همان گزارش پنل دستیار؛ بدون انتخاب فایل.
3. در صفحه «پرونده کارشناس»، کلیک روی نام → نمره معیارها، ردلاین‌ها، اقدامات اصلاحی (با امکان تیک‌زدن/حذف).

## نیازمندی‌ها

- Node.js ۱۸+ (برای `crm-qc`)
- فقط مرورگر (برای `HTML اصلی`)
- npm (xlsx به‌عنوان وابستگی)

## ارتباط ریت

- **تحلیل ریت تماس**: صفحه `call-analysis` — نمره، معیار، هیت‌مپ خطا، رتبه‌بندی، ردلاین‌ها، روند ماهانه — مبتنی بر ساختار پنل.
- **پرونده کارشناس**: مشاهده + ثبت/تغییر وضعیت اقدامات اصلاحی، نرخ هر معیار در تماس‌ها.
- **فایل‌های فعال**: `/api/calls/analysis`، `/api/actions?agent=...`

## توسعه

- `crm-qc/shared/reports.js` — موتور گزارش/تحلیل (بین سرور و مرورگر مشترک)
- `crm-qc/shared/parseQc.js` — پارس اکسل QC (بین سرور و مرورگر مشترک)
- `crm-qc/public/pages/callAnalysis.js` — صفحه‌ی تحلیل مشترک
- همگام‌سازی خودکار میموریر: وقتی فایل در `crm-qc/` ویرایش بشود، به `HTML اصلی/` هم کپی کن.


## بازه‌ی سراسری و گزارش‌های عملکرد (۱۴۰۵/۰۷/۲۰)

- بالای برنامه «از/تا تاریخ بررسی» و بازه‌های آماده وجود دارد؛ کنار هر دو فیلد تقویم جلالی باز می‌شود. انتخاب تاریخ با جابه‌جایی بین صفحه‌ها حفظ می‌شود و داشبورد، گزارش‌ها، پرونده، سوابق، آمار مرکز داده و تحلیل تماس همان بازه را نشان می‌دهند. برای دیدن کل داده «همه تاریخ‌ها» یا «حذف بازه» را انتخاب کنید.
- دکمه‌ی «اعمال بازه» حذف شده است: بازه با `Enter`، تغییر فیلد یا انتخاب «بازه آماده» اعمال می‌شود و یادداشت کنارش وضعیت را می‌گوید («در حال بروزرسانی گزارش‌ها…»، «روی همه گزارش‌ها اعمال شد»). چیدمان نوار بالا مرتب شده: وضعیت بازه و تاریخ امروز یک طرف، فیلدهای تاریخ و تقویم وسط، بازه‌ی آماده و دکمه‌های «امروز/پاک‌کردن» طرف دیگر.
- «بازه آماده ماه مالی» از تب `Fiscal_Months` شیت خوانده می‌شود (از چندم تا چندم = کدام ماه مالی): گزینه‌های `ماه مالی جاری`، `ماه مالی قبل` و تک‌تک ماه‌ها. این ردیف‌ها را می‌توان مستقیم روی شیت یا از صفحه‌ی «مدیریت پایه» (با ساخت خودکار ۱۲ ماه) نوشت؛ ردیف با تاریخ نامعتبر یا بازه‌ی وارونه نادیده گرفته می‌شود.
- منوی همبرگری در همه‌ی اندازه‌ها **پیش‌فرض بسته** است و با کلیک باز می‌شود؛ با `Escape`، کلیک بیرون منو، دکمه‌ی بستن یا رفتن به صفحه‌ی دیگر بسته می‌شود. جایگذاری فیلترها در همه‌ی صفحه‌ها یکدست شده (نوار فیلتر بدون خط جداکننده و هم‌تراز با عنوان صفحه).
- مبنای تاریخ تماس، تاریخ بررسی/ثبت فرم است؛ تاریخ انجام تماس جدا نگهداری می‌شود. روزهای ابتدا و انتها داخل بازه‌اند. تاریخ نامعتبر یا بازه‌ی معکوس اعمال نمی‌شود؛ رکورد فاقد تاریخ معتبر فقط در نمای همه‌ی تاریخ‌ها می‌آید و مرکز داده تعداد آن را اعلام می‌کند.
- در گزارش تماس، `1` = رعایت، `0` = عدم رعایت و `-` = موضوعیت نداشته؛ **نرخ‌ها فقط بر مبنای `1 + 0`** هستند. سلول خالی «ثبت‌نشده» است، نه صفر و نه `-`. نمره‌ی خالی در میانگین نیست؛ صفر واقعی در میانگین هست.
- فیلتر یک کارشناس، جدول تماس‌به‌تماس با نام شریک، نمره و مقادیر واقعی المان‌ها را نمایش می‌دهد. تعداد ردلاین در جدول فردی و گزارش تیم/کارشناس قابل کلیک است؛ بدون ردلاین `-` نمایش داده می‌شود. خروجی اکسل هم شمارش موضوعیت‌نداشته و جزئیات تماس‌ها را دارد.
- پرونده همه‌ی کارشناسان ثبت‌شده، از جمله بدون ریت و بایگانی، را با فیلتر تیم نشان می‌دهد. جدول‌های تاریخ‌محور و فایل‌محور حذف شده‌اند؛ کارت معیارها و ردلاین، سوابق تیکت/سوشال و اقدامات اصلاحی باقی‌اند. «جزئیات بیشتر» هر تماس، المان‌ها، شماره، تاریخ بررسی و زمان را باز می‌کند. زمان شنود به‌جای مدت واقعی مکالمه نمایش داده نمی‌شود؛ اگر فقط شنود ثبت شده باشد برچسب جدا دارد.
- آمار تیم از تیم **فعلی مدیریت کارشناسان** محاسبه می‌شود، بدون بازنویسی تیم ذخیره‌شده در سوابق. نام‌های واردشده‌ای که در مدیریت ثبت نشده‌اند مشخص‌اند و بدون تیم معتبر، به هیچ تیمی حدسی منتسب نمی‌شوند.
- در تحلیل تماسِ «همه تیم‌ها» فقط دو نمودار اول حذف شده‌اند؛ سایر گزارش‌ها باقی‌اند. ابزار مستقل «گزارش تماس» هم بازه را دریافت می‌کند، اما دیتایش با دیتای QC ادغام نمی‌شود. آمار قدیمی فاقد ریز تاریخ در حالت بازه‌دار با هشدار پنهان می‌شود، نه اینکه به‌عنوان گزارش فیلترشده ارائه شود.
- فیلتر نمایش، بک‌اپ یا پاک‌سازی را بی‌صدا محدود نمی‌کند؛ این عملیات همچنان بازه و تأیید مستقل خود را دارند.

### به‌روزرسانی داده‌های قبلی

فایل‌های پوشه‌ی `crm-qc/data/calls/` با نسخه‌ی جدید پارسر خودکار دوباره خوانده می‌شوند. برای اکسل‌هایی که قبلاً **در مرورگر آپلود** شده‌اند و تاریخ بررسی اشتباه ذخیره شده، اصل همان اکسل را از مرکز داده دوباره آپلود کنید؛ تاریخ واقعیِ ذخیره‌نشده را نمی‌توان از رکورد قدیمی حدس زد. قبل از بازآپلود از داده‌های خود بک‌اپ بگیرید. بازآپلود همان نام فایل جایگزین است و تعداد را تکراری نمی‌کند؛ تماس‌های مستقل با شماره/روز یکسان حذف نمی‌شوند.

### تست

```bash
npm --prefix crm-qc ci
npm --prefix crm-qc test          # محاسبات + API واقعی/آفلاین + UI هر دو نسخه
npm --prefix crm-qc run test:unit # فقط محاسبات، اکسل نمونه و کنترل همگامی
```

تست API سرور و دیتای موقت مستقل می‌سازد؛ فایل `data/store.json` و فایل‌های واقعی کاربر را تغییر نمی‌دهد. تست UI از jsdom و کنترل چرخه‌ی نمودار استفاده می‌کند. علاوه بر این، بررسی واقعی Chromium با Chart.js روی HTTP، فایل آفلاین، دسکتاپ، موبایل و فریم گزارش تماس انجام شده است.

کنترل مرجع فایل نمونه: **۸۱ ریت مستقل**؛ روز بررسی **۱۴۰۵/۰۶/۲۰ = ۳۹ ریت** (نه ۹ ردیف با تاریخ انجام تماس). فایل Excel نمونه هنگام خواندن هشدار ZIP از SheetJS چاپ می‌کند؛ خواندن ۸۱ ردیف و تطابق خروجی سرور/مرورگر در تست بررسی می‌شود.


## مدیریت و آرشیو ماهانه، پروفایل قابل اشتراک و حالت روشن

- در **مدیریت کارشناسان**، اکسل نمونه و راهنما دانلود می‌شود. «ویرایش» نام، تیم، داخلی و زیرمجموعه را تغییر می‌دهد؛ ارقام فارسی داخلی پشتیبانی می‌شوند. داخلی نامعتبر یا تکراری، هیچ تغییر نیمه‌کاره‌ای در نام/تیم ایجاد نمی‌کند. تغییر نامِ تأییدشده سوابق و نام قبلی را حفظ می‌کند.
- «حذف تمام کارشناسان» با نوشتن `حذف` و تأیید صریح انجام می‌شود؛ هم فعال‌ها و هم بایگانی‌ها حذف می‌شوند، **نه ریت‌ها و نه کارشناسان QC**. اسامی یکسان که دوباره ثبت شوند، سوابقشان قابل بررسی است.
- نام نمایشی فرم تماس فروش در گزارش، پرونده و Excel **Telesales** است. شناسه‌ی داخلی `tele` و کلید `callFeedbacks` برای سازگاری بک‌اپ‌ها تغییر نکرده‌اند. واژه‌ی فارسی قدیمی در متن کد و رابط با «ریت» جایگزین شده؛ نام فیزیکی فایل قدیمی ریشه برای لینک‌های قبلی حفظ شده است.
- **تغییر المان‌ها** مربوط به ریت تماس تیم‌هاست: نام نمایشی، نام ستون Excel، افزودن/حذف و فعال‌سازی دوباره. تنظیم پیش‌فرض هر فرم و تنظیم اختصاصی هر تیم موجود است. شناسه‌ی المان ثابت می‌ماند و نام قبلی ستون همچنان برای ورودی‌های قدیمی شناخته می‌شود. حذف از فرم فعال، مقادیر ثبت‌شده‌ی قدیمی را پاک نمی‌کند. نمره‌ی کلی از خود فایل می‌آید؛ این صفحه فقط ساختار المان‌ها، ستون‌های بررسی و محاسبه‌ی نرخ‌های `1/0/-` را تنظیم می‌کند، نه بازنمره‌دهی خودکار سوابق یا تغییر فرمول تأییدشده‌ی تیکت/سوشال.
- کلیک روی کارشناس، **پروفایل پاپ‌آپ** با بازه‌ی داده‌ی واقعاً بارگذاری‌شده باز می‌کند. خلاصه‌ی عملکرد، معیارها، ردلاین‌ها، نمودار، همه‌ی سوابق و جزئیات ریت‌ها، نظر QC و اقدامات قابل بررسی‌اند. بازه را از خود پاپ‌آپ هم می‌توان تغییر داد. «دانلود عکس کامل» تمام جداول/جزئیات را در PNG می‌آورد؛ ناحیه‌های اسکرول یا جزئیات بسته باعث بریده شدن سوابق نمی‌شوند. در بازه‌های بسیار بزرگ تصویر طولانی است؛ Excel نیز موجود است.
- **بک‌اپ ماهانه:** در مرکز داده، سال/ماه یا بازه‌ی دلخواه انتخاب کنید. ورود JSON/Excel پیش از هر تغییری، انتخاب **افزودن** یا **جایگزینی** و تأیید می‌خواهد. افزودنِ بک‌اپ، دیتای ماه‌های دیگر، تنظیمات و تیم/داخلی فعلی را حفظ می‌کند. جایگزینیِ بک‌اپ، کل محتوای شرح‌داده‌شده را جایگزین می‌کند و یک تأیید خطر جدا دارد. جایگزینیِ Excel فقط مربوط به فایل‌های هم‌نام است. واردکردن مجددِ آرشیو مشابه، ریت‌ها را دوباره نمی‌شمارد؛ ریت‌های مستقلِ هم‌شماره/هم‌روز حفظ می‌شوند.
- واچر پوشه‌ی سرور نیز ورود فایل هم‌نامِ ماه جدید را به حذف تاریخچه تبدیل نمی‌کند. تغییر متادیتای فایل باعث بازخوانی می‌شود، اما سوابق ماه‌های دیگر باقی‌اند. برای اصلاح عمدیِ داده‌ی همان فایل، گزینه‌ی جایگزینی در مرکز داده موجود است.
- **MLM:** تفاوت حروف فارسی/عربی و فاصله/نیم‌فاصله فقط در صورت تطبیق یکتا حل می‌شود. نام مبهم، نام ثبت‌نشده و تعارض نوع فرم/تیم در مرکز داده اطلاع داده می‌شوند. تیم مقصدِ صریح برای نام‌های ثبت‌نشده قابل انتخاب است؛ تیم فرد شناخته‌شده بدون ویرایش مدیریت عوض نمی‌شود. در نمونه‌ی فعلی، مشکل دو نام صرفاً فاصله‌گذاری بود؛ اکنون ۸۱ ریت کل و ۳۹ ریت روز ۱۴۰۵/۰۶/۲۰ به MLM متصل‌اند.
- **تاریخ دستی:** پس از ورود بازه‌ی کامل و معتبر، خودکار اعمال می‌شود؛ دکمه‌ی اعمال/Enter هم موجود است. حالت انتظار، خطا و اعمال‌شدن مشخص است. تاریخ اشتباه/معکوس، داده‌ی بازه‌ی قبلی را به روز جدید منتسب نمی‌کند. پاسخ قدیمی و روتِ قبلی نمی‌توانند صفحه‌ی تازه را بازنویسی کنند.
- **لایت‌مود:** دکمه کنار تاریخ امروز است؛ انتخاب ذخیره می‌شود و نمودارهای موجود بدون تغییر داده به‌روزرسانی می‌شوند. فونت، نمودار، عکس و کتابخانه‌های گزارش مستقل محلی هستند. تنظیم جای آیکون KPIهای تحلیل تماس و چیدمان موبایل در هر دو حالت انجام شده است.

### کنترل مرورگر واقعی

تست خودکار اصلی با `npm --prefix crm-qc test` اجرا می‌شود و به مرورگر نصب‌شده نیاز ندارد. برای بازاجرای بررسی واقعی (Linux):

```bash
npm --prefix crm-qc install --no-save --package-lock=false playwright-core @sparticuz/chromium
# در ترمینال اول: npm --prefix crm-qc start
# در ترمینال دوم:
npm --prefix crm-qc run test:browser
```

این بررسی از سرور با نمونه‌ی همراه برنامه استفاده می‌کند؛ دانلود قالب/عکس/بک‌اپ و لغو پنجره‌ی بازیابی را آزمایش می‌کند، نه حذف یا جایگزینی دیتای کاربر. تست‌های عملیات مخرب روی مخزن موقت مستقل انجام می‌شوند. عکس‌ها و فایل‌های بررسی در `crm-qc/node_modules/.cache/browser-artifacts/` هستند و وارد Git نمی‌شوند.


## لوگوی سامانه

لوگوی اصلی `logo.png` ریشه (نسخه‌ی آبی اصلی) مبنای هدر، نشان کناری، آیکون Chrome/ICO، Apple touch، آیکون‌های ۱۹۲/۵۱۲ و نشان گزارش عملکرد است. آیکون شیلدِ رقیب حذف شده است. آیکون‌های عملیاتیِ تقویم/حذف/تیم همچنان کاربرد خود را نشان می‌دهند.

## «تأیید اطلاعات» حذف شد — منبع داده کجاست

دکمه‌ی **تأیید اطلاعات** از بالای صفحه حذف شد. دلیلش این است که سامانه حالا به شیت/سرور وصل است و
«نسخه‌ی مرورگر» جای خود را به یک منبع داده‌ی واحد داده است:

- نسخه‌ی Node: داده در `crm-qc/data/store.json` (و در صورت اتصال، روی شیت) ذخیره می‌شود.
- نسخه‌ی مستقل Apps Script: همه‌ی داده در تب‌های همان شیت است و کش فقط برای سرعت به کار می‌رود.
- جای «تأیید اطلاعات»، نشانگر **همگام‌سازی** در نوار بالا آمده است: هر ~۴۵ ثانیه `revision` داده پرسیده
  می‌شود و اگر کاربر دیگری چیزی ثبت کرده باشد، با یک کلیک داده‌ی تازه بارگذاری می‌شود.
- بک‌اپ ماهانه همچنان از برگه‌ی **مرکز داده** (خروجی JSON/اکسل) یا با کپی خود شیت گرفته می‌شود.

## ورود با رمز، نقش مدیر و دسترسی کارشناس QC

- صفحه‌ی جدید **مدیریت QC** (`#/qcadmin`، فقط مدیر): ساخت کاربر، تعیین رمز، نقش، فعال/غیرفعال کردن و
  مشخص کردن اینکه هر کارشناس QC کدام **داخلی‌ها/کارشناسان/تیم‌ها** را ببیند. خروجی اکسل هم دارد.
- تا وقتی هیچ کاربر فعالِ رمزدار نباشد، ورود خاموش است (مثل قبل). با ساخت اولین حساب مدیر، ورود اجباری
  می‌شود و کارت ورود روی برنامه می‌آید. حالت ورود (`auto`/`on`/`off`) در همان صفحه و در تب `Settings` شیت
  قابل تغییر است.
- **مدیر** همه‌ی صفحه‌ها و همه‌ی داده‌ها را می‌بیند (داشبورد و گزارش‌ها بدون محدودیت) و چهار صفحه‌ی
  «تغییر المان‌ها»، «مدیریت پایه»، «مدیریت کارشناسان» و «مرکز داده» فقط برای مدیر فعال‌اند.
- **کارشناس QC** فقط صفحه‌های عملیاتی را می‌بیند و داده‌اش به کارشناسان مجاز محدود است؛ ثبت/ویرایش
  ارزیابی هم فقط برای همان کارشناسان ممکن است. نام کاربر واردشده به‌صورت پیش‌فرض در فیلد «کارشناس
  کنترل کیفیت» فرم‌ها می‌نشیند و برای نقش QC قفل است.
- رمزها اثر انگشت SHA-256 با نمک هستند و در تب `QC_Users` شیت (یا `store.json` در نسخه‌ی Node) نگه داشته
  می‌شوند؛ نوشتن رمز به‌صورت متن ساده روی شیت هم پذیرفته می‌شود تا مدیریت بدون باز کردن برنامه ممکن باشد.
- **نام المان‌ها** هم فارسی و هم در فایل اکسل دریافتی قابل تغییر است: تب `Elements` دو ستون `label`
  (نام فارسی) و `excelKey` (نام ستون اکسل) دارد و تغییر `excelKey` نام قبلی را خودکار به `aliases`
  منتقل می‌کند تا سوابق قدیمی نشکنند. این ردیف‌ها را می‌توان مستقیم روی شیت ویرایش کرد.
- برای سبک‌شدن محاسبات، تب `Monthly_Summary` خلاصه‌ی آماده‌ی هر «کارشناس × ماه» را نگه می‌دارد و
  تحلیل‌های سنگین در `CacheService` کش می‌شوند؛ بازسازی دستی از منوی شیت
  (`بازسازی تب خلاصه ماهانه`) ممکن است.

## یک ستون برای هر کارشناس QC (بدون ویرگول)

- در تب `Agents` هر کارشناس QC یک **ستون اختصاصی** دارد با سرستون `QC: نام`؛ در ردیف هر کارشناس
  با انتخاب «✓» از لیست کشویی مشخص می‌کنید چه کسی او را بررسی می‌کند. دیگر لازم نیست نام‌ها را در
  یک سلول با ویرگول بنویسید و ستون متنی قدیمی `qcAgents` هم دیگر ساخته نمی‌شود (اگر از نسخه‌ی
  قبلی مانده باشد، هنگام اولین ذخیره به ستون‌های اختصاصی منتقل و حذف می‌شود).
- هر دو طرف هم‌زمان‌اند: تیک روی شیت در همان لحظه در صفحه‌ی «مدیریت QC» و «مدیریت کارشناسان»
  دیده می‌شود و برعکس، تیک‌های اپ روی شیت نوشته می‌شوند. افزودن، تغییر نام یا حذف یک کارشناس QC
  ستونش را روی شیت می‌سازد/تغییر می‌دهد/برمی‌دارد و تیک‌های بقیه دست‌نخورده می‌مانند.
- در صفحه‌ی «مدیریت کارشناسان» هم به‌جای کادر متنی، دکمه‌ی **+** باز می‌شود و کارشناسان QC را تیک
  می‌زنید؛ ایمپورت اکسل هم ستون‌های `QC: نام` را می‌خواند و اکسل نمونه همین ساختار را دارد.

## آیکون سربرگ مرورگر

- لوگوی خود سامانه روی تب مرورگر می‌نشیند: در نسخه‌ی وب `favicon.png`/`favicon.ico` و در
  نسخه‌ی Apps Script هم `setFaviconUrl` روی خروجی `doGet` (پیش‌فرض: `favicon.png` مخزن).
  اگر آدرس دیگری خواستید، مقدار `QC_GAS_FAVICON_URL` را در Script Properties بگذارید.
- اگر صفحه داخل بسته‌ی اکستنشن یا محیطی باز شود که فایل آیکون در دسترس نیست، آیکون از خود
  `logo.png` ساخته می‌شود تا آیکون پیش‌فرض مرورگر/اکستنشن روی تب نماند.

## سرعت: کش تب‌به‌تب، خواندن جزئی و حذف محاسبات تکراری

- **کش هر تب با نسخه‌ی خودش:** پیش‌تر کل دیتابیس یک‌جا کش می‌شد و چون از سقف اندازه
  بزرگ‌تر بود، عملاً هر درخواست (حتی یک گزارش تکراری) هر ۱۶ تب را از شیت می‌خواند.
  حالا هر تب جداگانه و با شماره‌ی نسخه‌ی خودش در `CacheService` نگه داشته می‌شود؛
  نوشتن یک ریت فقط نسخه‌ی همان تب را عوض می‌کند و بقیه‌ی داده گرم می‌ماند، پس
  `bootstrap` بعد از هر ذخیره **هیچ تبی را از شیت نمی‌خواند**.
- **خواندن جزئی:** هر مسیر نوشتنی فقط تب‌های موردنیاز خودش را بارگذاری می‌کند
  (ثبت تیکت ← `Tickets` + تنظیمات/کارشناسان/ماه مالی؛ نه `Calls` و `Socials` و `Actions`).
  تور ایمنی: اگر مسیری تبی را تغییر دهد که بارگذاری نشده، همان درخواست با خواندن
  کامل تکرار می‌شود تا هیچ تغییری گم نشود و هیچ تبی پاک نشود.
- **بدون کپی عمیق کل دیتابیس:** پیش از اجرای هر نوشتن، اثرانگشت JSON هر تب گرفته
  می‌شود؛ مقایسه و دیفِ سطری فقط برای تبِ عوض‌شده انجام می‌شود (پیش‌تر دو کپی کامل
  به‌علاوه‌ی دو رشته‌سازیِ کل داده در هر درخواست ساخته می‌شد).
- **تب خلاصه‌ی ماهانه:** در نوشتن‌های پیاپی حداکثر هر ۵ دقیقه یک‌بار بازسازی می‌شود
  (نه برای هر ریت) و در مسیرهای سنگین مثل بازگردانی بک‌آپ، ایمپورت یا ویرایش کارشناسان
  بی‌درنگ. منوی «بازسازی تب خلاصه ماهانه» همیشه فوری و کامل است.
- **ویرایش مستقیم روی شیت** (یا منوی «بازخوانی از شیت») کش همه‌ی تب‌ها را باطل می‌کند،
  پس داده‌ی دستیِ شما همیشه بر کش اولویت دارد.
- **نسخه‌ی Node/سرور:** نتیجه‌ی گزارش‌ها، داشبورد، خلاصه‌ی ماهانه، وضعیت داده و
  پرونده‌ی کارشناسان با کلید «نسل داده + کاربر + فیلترها» حافظه می‌شود و با هر نوشتن
  پاک می‌شود؛ کپی محدودشده‌ی داده‌ی هر کارشناس QC هم حافظه دارد و `store.json`
  فشرده و debounce‌شده نوشته می‌شود.
- **کلاینت، رفت‌وبرگشت کمتر در هر ثبت:** پیش‌تر هر «ثبت ارزیابی» چهار رفت‌وبرگشت داشت
  (POST + `/api/revision` + `/api/bootstrap` + فهرست). حالا شماره‌ی نسخه در همان پاسخ نوشتن
  برمی‌گردد و شمارش پاورقی همان‌جا اصلاح می‌شود، پس فقط POST و فهرست می‌ماند — در Apps Script
  که هر رفت‌وبرگشت چند صد میلی‌ثانیه است، این تفاوت کاملاً محسوس است.
- **کلاینت:** شمارش پاورقی از خودِ پاسخ `bootstrap` می‌آید، نه یک درخواست جداگانه به
  `/api/data/status` که هر بار کل داده را جارو می‌کرد (این درخواست بعد از هر ثبت ریت تکرار می‌شد).
- **اندازه‌گیری** روی داده‌ی نمونه‌ی ۳۰۰۰ تیکت + ۳۰۰۰ سوشال + ۶۰۰۰ تماس + ۱۲۰۰ اقدام
  در محیط آزمایش (که در آن خواندن شیت تقریباً رایگان است): ثبت ریت از `439ms` به `41ms`،
  `bootstrap` گرم از `106ms` به `29ms`، گزارش تکراری از `109ms` به `27ms` و تعداد
  خواندن‌های شیت در هر ریت از ۱۶ تب به **صفر** رسید (فقط نوشتن `Tickets` و `Meta`).
  در Apps Script واقعی که خواندن هر تب چند صد میلی‌ثانیه هزینه دارد، اثر این تغییر
  چند برابر بیشتر است.
- پس از جای‌گذاری `Code.gs` تازه، یک‌بار از منوی شیت **«آماده‌سازی سامانه مستقل»** یا
  «بازخوانی از شیت» را بزنید تا کش‌ها با ساختار جدید ساخته شوند.

## کار هم‌زمان چند کارشناس QC

- نوشتن‌ها زیر قفل اجرا می‌شوند و داده را تازه می‌خوانند؛ خواندن‌ها بدون قفل و از کش سرو می‌شوند.
- اگر رکوردی بعد از باز شدن فرمِ شما توسط شخص دیگری ویرایش شده باشد، سامانه به‌جای بازنویسی کورکورانه
  `409` می‌دهد و گفت‌وگویی نشان می‌دهد با دو راه: «بارگذاری نسخه‌ی تازه» یا «تغییرات من جایگزین شود».
- ویرایش هم‌زمان المان‌ها با نسخه‌ی کهنه هم `409` می‌گیرد تا پیکربندی کسی پاک نشود.
- تنظیمات محلی رابط (بازه‌ی تاریخ، فیلترها، ستون‌های جدول) با کلید اختصاصی هر کاربر ذخیره می‌شود، پس
  محیط کار یک نفر روی نفر دیگر اثر نمی‌گذارد.
- `بستن همه نشست‌های فعال (خروج اجباری)` از منوی شیت، همه‌ی توکن‌ها را یک‌جا باطل می‌کند.

## گزارش تماس در نسخه‌ی Apps Script

گوگل وب‌اپ را داخل فریم شنی سرو می‌کند و فریم تودرتو با آدرس `/exec` با خطای **`refused to connect`**
یا **`Sorry, unable to open the file at this time`** رد می‌شود. به همین دلیل در نسخه‌ی مستقل، ابزار
«گزارش تماس» با `google.script.run` از خود سامانه گرفته و HTML آن داخل یک فریم محلی (`srcdoc`) نشان
داده می‌شود؛ نه فریم تودرتوی `/exec` لازم است و نه تب جدید. بازه‌ی تاریخ و حالت رنگ هم منتقل می‌شوند،
و دکمه‌ی «تب جدید» فقط برای وقتی است که بخواهید همان ابزار را جدا باز کنید. در نسخه‌ی Node همان برگه
گزارش را داخل فریم هم‌ریشه نشان می‌دهد.


## اتصال دوسویه به Google Sheets

در نسخه‌ی سرور، منوی **اتصال به گوگل شیت** اضافه شده است. سامانه می‌تواند از تب‌های شیت داده‌ی کارشناسان، تیکت، سوشال، تماس، اقدامات و تنظیمات را بخواند؛ ثبت‌های برنامه را هم به شیت بفرستد و گزارش عملکرد را در تب جداگانه بسازد.

- پیاده‌سازی سرور: `crm-qc/googleSheets.js` و APIهای `/api/sheets/*`
- رابط تنظیم اتصال: `crm-qc/public/pages/sheets.js`
- Apps Script آماده: `crm-qc/apps-script/Code.gs`
- راهنمای نصب، راه‌اندازی اولیه و محدودیت‌ها: `crm-qc/apps-script/README.md`

**نکته‌ی معماری:** در این مسیر، Node روی یک میزبان اجرا می‌شود و هر ۶۰ ثانیه (قابل تنظیم) با شیت همگام می‌شود؛ شیت مخزن داده و محل گزارش است و `crm-qc/apps-script/Code.gs` فقط API/منو/گزارش سبک می‌دهد.

## نسخه‌ی کاملاً مستقل روی Google Sheets (بدون Node)

اگر هدف یک **لینک اختصاصی Apps Script** است که کل سامانه را روی شیت بالا بیاورد و هر داده در تب خودش باشد، از `crm-qc/apps-script-full/` استفاده کنید:

- `Code.gs` — بک‌اند مستقل (ورود با رمز، نشست‌ها، محدودسازی داده، کش تحلیل): خواندن/نوشتن تب‌ها با قفل هم‌زمانی، روتر همان APIها، منوی شیت و `doGet`
- `Index.html` — رابط کامل سامانه با همه‌ی کتابخانه‌ها/فونت‌ها به‌صورت جاسازی‌شده
- `CallReport.html` — ابزار «گزارش تماس روزانه» در صفحه‌ی مستقل (با دکمه‌ی بازگشت به سامانه) و تنظیمات در دو تب اختصاصی
- ساخت دوباره: `npm --prefix crm-qc run build:apps-script`

تب‌های دیتابیس (۲۳ تب): `Agents`, `Tickets`, `Socials`, `Calls`, `QC_Agents`, `Actions`, `Reminders`, `Action_Types`, `Settings`, `Lists`, `Criteria`, `Meta`, `Call_Metadata`, `Call_Report_Experts`, `Call_Report_Access`, `Fiscal_Months` (بازه‌های ماه مالی), `QC_Users` (کاربران، رمزها و دسترسی‌ها), `Elements` (نام فارسی و ستون اکسل المان‌ها), `Monthly_Summary` (خلاصه‌ی ماهانه‌ی آماده). چهار تب آخر را می‌توان مستقیم روی شیت هم نوشت/ویرایش کرد.

در این نسخه پوشه‌ی محلی `data/calls` و واچر خودکار وجود ندارد؛ ورودی اکسل ریت تماس از برگه‌ی **مرکز داده** آپلود می‌شود. راهنمای گام‌به‌گام فعال‌سازی، استقرار با `clasp`، محدودیت سهمیه و امنیت لینک در [`crm-qc/apps-script-full/README.md`](crm-qc/apps-script-full/README.md) است.

پیشنهاد شروع: در تب اتصال، Web App را تنظیم کنید؛ از منوی شیت توکن بسازید؛ سپس یک بار «ارسال اطلاعات سامانه به شیت» را برای پرکردن شیت فعلی انجام دهید. بعد از بک‌اپ و کنترل داده‌ها، اگر می‌خواهید ویرایش/حذف ردیف در شیت مرجع اصلی باشد، سیاست **شیت مرجع** را انتخاب کنید. سیاست **ادغام امن** به‌صورت پیش‌فرض است و ردیفی را صرفاً به‌خاطر نبودن در شیت حذف نمی‌کند.

**امنیت و محدودیت:** توکن Web App و JSON مربوط به Service Account در فایل‌های محلی `crm-qc/data/` هستند و در Git ثبت نمی‌شوند. فایل `sheets-config.example.json` فقط نمونه است. لایه‌ی ورود با رمز و نقش‌ها (مدیر/کارشناس QC) داخل خود سامانه پیاده شده و در هر دو نسخه کار می‌کند (رمزها hash‌شده در تب `QC_Users`)؛ با این حال سطح دسترسی Deploy در گوگل را هم محدود نگه دارید و رمزها را در Git یا پیام‌رسان منتشر نکنید. Google Sheets برای حجم کم تا متوسط مناسب است، نه دیتابیس تراکنشی پرسرعت؛ همگام‌سازی لحظه‌ای نیست و با فاصله‌ی انتخابی انجام می‌شود. برای اجرای Apps Script ممکن است سیاست سازمان اجازه‌ی Web App با دسترسی بیرونی ندهد؛ در آن صورت از Service Account استفاده کنید.

تست‌های نگاشت و ادغام شیت، سیاست حذف، توکن و redirect در `npm --prefix crm-qc test` هستند.
